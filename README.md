# paas-e2e

Сквозные проверки живой платформы PaaS: ходим её публичным API так же, как это
делает пользователь с машины, и падаем, если что-то из этого перестало
работать. История — `E2E-01`, эпик — `EPIC-19` в метарепо
(`meta/products/paas/docs/user-stories/epics/EPIC-19-e2e-checks/`).

**Проверки неразрушающие.** Ни один сценарий ничего не создаёт, не меняет и не
удаляет: после прогона состояние платформы то же, что до него. Поэтому их
безопасно гонять по проду и повторять сколько угодно раз.

## Что проверяется

| Сценарий | Что ломается, если он красный |
|---|---|
| `TestPublicEntrypointsAnswer` | внешние входы: веб-интерфейс, вход в аккаунт, описание API (DNS, сертификат, ingress) |
| `TestRequestWithoutTokenRefused` | данные организации открыты без предъявленного доступа |
| `TestOrganizationVisible` | аутентификация машинным доступом и домен организаций |
| `TestProductsListed` | домен продуктов |
| `TestServicesListed` | домен сервисов |
| `TestServiceVersionsReadable` | линия доставки не оставляет следа — версии перестали появляться |
| `TestPublishedProtocolsCompatibleWithThemselves` | реестр протоколов: чтение контракта и сверка совместимости |
| `TestClustersConnected` | платформа потеряла связь с кластером — катить некуда |
| `TestDeployedWorkloadsHealthy` | выкаченный процесс без готовых реплик — прод лежит |
| `TestDeclaredHostsReachable` | сгенерированные выкаткой домены не отвечают снаружи |

Отчёт различает **«не ответила»** (сеть, TLS, таймаут — авария доступности) и
**«отказ»** (платформа жива, но не пустила или сломалась внутри): виновник
разный, и по логу это должно быть видно сразу.

## Запуск

```sh
PAAS_API_TOKEN=<машинный или личный токен> go test -v ./...
```

Со своей машины отдельный токен заводить не нужно: если переменные не заданы,
набор берёт сохранённый вход `paas-cli` из его файла
(`<UserConfigDir>/paas-cli/session`, после `paas-cli auth login`) и
предъявляет его так же, как сам CLI:

```sh
go test -v ./...
```

Без доступа прогон **падает**, а не пропускается: молча зелёная проверка хуже
её отсутствия.

### Переменные

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PAAS_API_TOKEN` | — | машинный или личный токен платформы |
| `PAAS_SESSION_TOKEN` | — | сессия identity-провайдера (альтернатива токену) |
| `PAAS_API_URL` | `https://api.paas.traumtech.ru` | адрес API |
| `PAAS_WEB_URL` | `https://paas.traumtech.ru` | адрес веб-интерфейса |
| `PAAS_AUTH_URL` | `https://auth.paas.traumtech.ru` | адрес входа в аккаунт |
| `PAAS_E2E_TIMEOUT` | `20s` | таймаут одного запроса |

## Свежий кластер под прогон

Сценариям, которым нужен настоящий кластер, прогон поднимает **свой одноузловой
кластер** и сносит его в конце. Так решается уборка: платформа умеет удалить
сервис, но **не умеет снять выкатку** — namespace с процессами остаётся работать
в кластере. Вместе с машиной исчезает всё, что платформа успела туда положить,
и это работает даже когда сценарий упал посередине.

Кластер каждый раз новый, а **адрес, корневой сертификат и токены — те же**:
их выпускает разовая подготовка `hack/bootstrap-once.sh`, дальше они живут в
секретах. Поэтому подключение кластера на платформе заводится **один раз** и
переживает пересоздание — иначе каждый прогон плодил бы новую запись, а
отзывать их платформа пока не умеет.

```sh
hack/bootstrap-once.sh     # разово: адрес, записи DNS, корневой сертификат, токены
hack/cluster-up.sh         # поднять кластер прогона
go test -v -tags cluster ./...
hack/cluster-down.sh       # снести (идемпотентно, зовётся и перед подъёмом)
```

Что кладётся в свежий кластер: права платформы — **ровно те, что она сама
объявляет требуемыми** (если начнёт ходить за большим, прогон это увидит);
контроллер входа `ingress-nginx` и `cert-manager` тех же версий, что стоят в
постоянном кластере; выпускающий `letsencrypt-prod` — имя задано платформой,
она проставляет его аннотацией на каждом сгенерированном Ingress.

Записи DNS — `e2e.traumtech.ru` и `*.e2e.traumtech.ru` на зарезервированный
адрес. Wildcard нужен потому, что хост выкатки складывается из имени сервиса, а
каждый прогон заводит сервис заново. Сертификаты выпускаются **боевым** Let's
Encrypt: имена каждый раз новые, поэтому в лимит повторных выпусков не упираемся,
а проверять путь на тестовом ACME смысла нет.

## Расписание

Два прогона с разными расписаниями. `.github/workflows/e2e.yml` — неразрушающий,
раз в сутки в 06:00 UTC, плюс запуск по кнопке (`workflow_dispatch`) и на пуш в
`main`. `.github/workflows/e2e-cluster.yml` — со свежим кластером, в 05:00 UTC,
часом раньше: если сломан кластерный путь, к утру это уже видно. Снос кластера
стоит с `if: always()`, а сами прогоны сериализованы — адрес у кластера один. Секрет `PAAS_API_TOKEN` — личный токен
проверок; он не принадлежит ни одному сервису, поэтому его отзыв не задевает
выкатки. О неуспешном прогоне уведомляет сам GitHub; отдельный канал
уведомлений — roadmap эпика.
